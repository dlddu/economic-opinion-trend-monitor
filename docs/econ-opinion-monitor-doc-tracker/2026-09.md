
# 경제 여론 추세 모니터 문서 체계 상태 추적 — 2026-09

> 직전: [2026-08.md](./2026-08.md)

> 이 문서는 가치 → PRD → AC → 테스트의 연결 상태를 추적하는 핵심 산출물이다.

## 현재 상태 요약
- 정의된 가치: **5개** (V1~V5)
- PRD: **3개** (수집 / LLM 분석 / 정규화·집계·시각화)
- Acceptance Criteria: **21개** (가치 연결됨: 21개 / 미연결: 0개)
- 테스트 문서: **3개** (AC 커버됨: 21개 / 미커버: 0개)
- **건강 상태**: ⚠️ **위험 있음** — 제품 소유자 미지정으로 전 가치가 고아 가치 상태.
  연결 구조 자체(가치↔PRD↔AC↔테스트)는 끊김 없이 완전함.
- **문서↔구현 정합성**: 위 건강 상태의 ✅는 **문서 체계**(가치↔PRD↔AC↔테스트 연결)만을
  뜻한다. 문서가 정의한 동작을 구현이 충족하는지는 별도(reconciler 정합성 루프, 모델
  `tbm_econ-opinion-monitor-docs-impl`)로 추적한다. 아래 현황은 **실측이며 착지분과 잔여분을
  갈라 적는다** — 하나로 뭉친 현재형 요약("21개 AC 전부가 미구현")은 착지가 쌓여도 문구가 바뀌지
  않아 `576438e`(2026-07-24) 이후 7주간 정체했고, 그 사이 같은 문서의
  [AC↔e2e 1:1 매핑표](#ace2e-11-매핑표)가 세 AC를 `✅ 착지`로 적어 **한 파일이 스스로를 반증**했다
  (2026-09-18 정정). 그래서 각 잔여 항목에 **관측 좌표(파일 ∋ 문자열)** 를 단다 — 구현이 착지하면

## e2e 매핑
<!-- registry: tbm_econ-opinion-monitor-scenario-e2e, tbm_econ-opinion-monitor-e2e-mock-policy -->

> reconciler 모델 `tbm_econ-opinion-monitor-scenario-e2e`가 지목한 **SSOT 절**이다. 테스트 문서의
> **시나리오**(`docs/econ-opinion-monitor-test-*.md` 의 `### 시나리오 N:` 헤딩)와 `tests/e2e/specs/`
> 의 spec 파일이 1:1로 대응하는지를 여기 기록된 등재·집계로 판정한다. 아래 표는 **계획이 아니라
> 실측**이다 — 로드맵의 목표 배정은 [AC↔e2e 1:1 매핑표](#ace2e-11-매핑표)를 보라.
> `python3 tests/e2e/check_scenario_mapping.py`(= `make lint-scenario-mapping`, CI `build` 잡의
> `make lint` 이 실행)가 이 절과 실제 파일·테스트 문서를 대조해 어긋나면 실패한다.
>
> **축 주의**: 이 절은 2026-09-09 이전까지 **AC 축**이었다(모델의 옛 유형 `…-ac-e2e`). 판정 단위가
> 시나리오로 바뀌었으므로 그 이전의 이력 행·로드맵 표에 남은 AC 기준 서술은 다른 축의 기록이다.
> 어떤 시나리오가 어떤 AC를 검증하는지는 **테스트 문서의 `검증 AC` 필드가 SSOT**이며, 그 연결의
> 완전성은 이 절도 게이트도 보지 않는다(모델 정의: "AC ↔ 시나리오 층은 판정 대상이 아니다").

### 매칭 규약
- **매칭 단위**: `tests/e2e/specs/` 최상위 `*.spec.ts` **파일**. 파일 안의 `test()` 개수는 자유다 —
  한 시나리오를 여러 케이스로 쪼개도 무방하다. `fixtures/`·`k8s/`·`run.sh`·`playwright.config.ts`·
  `package*.json`·`kind-config.yaml`·`check_scenario_mapping.py` 는 실행 하네스라 매칭 단위가 아니다.
- **시나리오 식별자**: `<문서 파일명>#시나리오 <N>` (서수 표기). 문서 중간에 시나리오가 삽입돼 번호가
  밀리면 **식별자가 바뀐 것**이므로 선언과 이 절의 표를 함께 갱신한다.
- **선언**: 각 spec 파일은 헤더 주석에 `// 검증 시나리오: <문서 파일명>#시나리오 <N>` 을 **정확히 한
  줄** 둔다. 시나리오를 주검증하지 않는 스모크·인프라 파일은 `// 검증 시나리오: 없음 (스모크/인프라)`
  로 선언하고 아래 비-시나리오 등재 표에 올린다. 매핑은 이 한 줄로 기계적으로 확인된다:
  `grep -h '^// 검증 시나리오:' tests/e2e/specs/*.spec.ts`
- **파일명은 강제하지 않는다**: 현행 3개는 AC 축 시절의 `ac<major>-<minor>-<슬러그>.spec.ts` 이름을
  그대로 쓴다. 이름이 아니라 **선언 한 줄**이 매핑의 SSOT이고, 개명은 로드맵 표의 파일 배정
  (`tbm_econ-opinion-monitor-docs-impl` 소관)과 함께 움직여야 해서 별도 슬라이스다.
- **세지 않는 것**: 셋업에서 다른 시나리오의 화면·경로를 경유하는 것은 검증으로 세지 않는다.
  선언된 시나리오만 센다.
- **네 통**: 모든 시나리오는 **매칭 · 예외 · 구현 대기 · 공백** 중 **정확히 하나**에 들어간다. 게이트가
  그 분할을 강제하므로 어떤 시나리오도 판정 없이 초록 아래 남지 못한다.

### 구현 대기 (미구현이라 관측 대상 없음)
시나리오가 기술하는 기능이 **아직 구현되지 않아** e2e가 관측할 대상 자체가 없는 시나리오(모델 규칙6).
예외(영구 면제)와 달리 **임시 등재**이며, 구현이 착지하면 1:1 판정 대상으로 복귀한다. 한 시나리오가
예외 목록과 이 표에 동시에 오를 수 없고 `check_scenario_mapping.py` 의 **규칙6** 이 그것을 CI에서
강제한다. **미구현의 해소는 이 모델의 몫이 아니다** — 구현은 `tbm_econ-opinion-monitor-docs-impl` 이
진다(모델 정의: "이 루프는 미구현을 해소하지 않는다").

판정 기준은 하나다: **그 시나리오의 "실행 단계 · 기대 결과"를 오늘 main 코드 위에서 관측할 대상이
있는가.** 한 절이라도 관측 대상이 없으면 구현 대기이고, 대상은 있는데 현행 e2e 하네스가 닿지 않을
뿐이면 [공백](#공백-11-대상-중-파일-없음)이다 — 공백은 **이 모델이 하네스를 넓혀** 닫고, 구현 대기는
담당 모델이 구현을 착지시켜야 풀린다. 둘을 한 통에 담으면 "누가 무엇을 해야 하는가"가 사라진다.

**해제 신호**는 이 등재가 조용히 낡는 것을 막는 장치다. 이 모델의 as-is는 `tests/e2e` 트리이고
to-be는 테스트 문서 + 이 문서라, 구현이 `go/`·`python/`·`web/` 에 착지해도 **어느 쪽 버전도 바뀌지
않아 재감지가 뜨지 않는다.** 그래서 "아직 미구현임을 보여 주는 문자열"을 좌표로 적어 두고, 게이트가
매 CI에서 그 문자열이 **아직 살아 있는지** 확인한다. 구현이 착지해 문자열이 사라지면
`make lint-scenario-mapping` 이 빨개지고 이 표를 다시 판정하도록 강제된다. 완전한 판별자는 아니고
**조기 경보**다 — 신호가 살아 있다고 미구현이 증명되지는 않지만, 사라지면 반드시 재판정한다.

**집계 배치가 섰지만 서빙 입력은 아직 픽스처 Gold다.** 다섯 건 중 어느 것도 서빙을 파이프라인

**매칭은 커버리지의 상한이 아니다 — 남은 관측 한계 하나를 명시해 둔다.** 공유 픽스처 Gold 는

## 구현 수렴 로드맵 (reconciler 정합성 루프)

> 이 절은 **문서 → 구현 수렴의 실행 순서**를 기록한다(제품 스펙 자체가 아니라 정합성 작업 계획).
> 출처: reconciler 모델 `tbm_econ-opinion-monitor-docs-impl` · task `rct_20260712-0001`.
> 등록 시점에 20개 AC 전부가 페이크/스텁 뒤 미구현 상태이며(README 부트스트랩 골격), 각
> 슬라이스는 후속 reconciler task로 구현·검증된다. 이 표는 **우선순위·순서만** 정하고,
> 슬라이스별 세부 작업 분해는 각 task의 계획 단계에서 확정한다.

### AC↔e2e 1:1 매핑 원칙
문서→구현 수렴은 **AC와 e2e spec 파일의 1:1 대응**을 기준으로 진행한다(리뷰어 지시 반영):

- **매칭 단위는 파일이다**: 1:1은 *테스트 케이스*가 아니라 `tests/e2e/specs/` 최상위
  `*.spec.ts` **파일** 단위로 센다. 한 AC의 spec이 여러 `test()`로 쪼개지는 것은 무방하지만,
  **한 파일이 여러 AC를 겸하면 분리 대상**이다. 파일 단위인 이유는 매핑이 `grep` 한 줄로
  기계 검증되기 때문이다 — 케이스 단위는 TypeScript를 파싱해야 하고, 그러면 규칙을 강제하는
  게이트를 만들 수 없다.
- **AC → 파일**: 예외 등재되지 않은 모든 AC는 자신을 주검증하는 spec 파일을 **정확히 하나**
  가진다.
- **파일 → AC**: 모든 spec 파일은 **정확히 하나의 AC**를 검증 대상으로 선언한다. AC 대신
  스모크·인프라를 검증하는 파일은 그렇게 선언하고 등재한다.
- **파생·위치**: 각 spec 파일은 test 문서 3종(`…-test-ingestion` / `-test-analysis` /
  `-test-aggregation-viz.md`)이 이미 정의한 1:1 시나리오(수집 7 · 분석 6 · 집계·시각화 8 = **21**)에서
  파생되어, `tests/e2e/specs/ac<major>-<minor>-<슬러그>.spec.ts` 로 구현된다.
- **추적 가능성**: 각 spec 파일은 헤더 주석에 `// 검증 시나리오: <문서 파일명>#시나리오 <N>` 을
  정확히 한 줄 둔다(2026-09-09 축 이관 전에는 `// 검증 AC: ACn.m` 이었다). 선언 규약·예외 등재·구현
  대기 등재·실제 상태 집계의 SSOT는 [e2e 매핑](#e2e-매핑) 절이며, `make lint-scenario-mapping` 이 그
  절과 실제 파일을 대조한다. 이 표가 배정하는 AC↔파일 대응은 그와 **축이 다른** 계획표다.
- **예외**: e2e 자동 검증이 곤란한 AC는 [e2e 매핑](#e2e-매핑) 절의 예외 목록에 사유·대체 검증
  수단과 함께 등재하고, 아래 표에서 파일을 배정하지 않는다.
- **슬라이스와의 관계**: 각 슬라이스는 자신이 **소유하는 AC들의 spec 파일을 신설·활성화**한다.
  화면 표면만 더하고 신규 AC를 소유하지 않는 슬라이스(`trace`·`reprocess`)는 새 1:1 매핑을 만들지
  않으며, 그 화면이 재노출하는 동작은 이미 소유 슬라이스의 spec이 검증한다. 구체 배정은 아래
  **AC↔e2e 1:1 매핑표**를 따른다.

### 전략: 대시보드 경로 수직 슬라이스 먼저 → 이후 화면 단위 확장
메달리온 데이터 흐름(Bronze→Silver→Gold→Go 서빙→web)에는 **하드 의존성**이 있다 — 분석은
Bronze 없이·집계는 Silver 없이·어떤 화면도 Gold 없이 실데이터를 낼 수 없다. 따라서 "화면부터"는
성립하지 않는다(화면 1개도 파이프라인 없이는 실데이터 불가). 먼저 가장 많이 배선된 대시보드
경로로 **파이프라인 척추를 종단 관통**해 스택 전체를 조기에 검증하고(통합 리스크 조기 노출·동작
데모 확보), 그 위에 화면을 **한계 파이프라인 비용(작은 것 우선)·가치 우선순위(V1→V3→V2→V4→V5)·
운영 의존성(reprocess 최후)** 순으로 붙인다. 대안 비교: 층별 수평(AC1 전부→AC2 전부→AC3 전부)은
마지막까지 사용자 대면 검증 결과가 없어 통합 리스크를 은폐하므로 배제한다.

### AC↔e2e 1:1 매핑표
21개 AC를 **AC별 전용 spec 파일**에 1:1로 배정한다(각 AC·각 파일 정확히 1회 등장). 파일은 대응
test 문서 시나리오에서 파생되며 모두 `tests/e2e/specs/` 아래 `ac<major>-<minor>-<슬러그>.spec.ts`

18개 파일명은 서로 유일하고, 예외 3건은 파일을 갖지 않는다.

**✅ 착지한 3건에 대한 주**: AC3.6·AC3.7·AC3.8은 순수 서빙·시각화 AC라 배치 파이프라인 없이 현행
e2e 하네스에서 검증 가능해 **소유 슬라이스보다 먼저 착지**했다. 슬라이스 6(`sentiment` 화면)·
7(`compare` 화면)·8(`fairness` 화면)은 이 세 AC의 spec을 **신설하지 않고**, 자기 화면이 붙을 때 같은
파일을 확장한다(새 파일을 만들면 규칙2 위반이다).

AC3.6·AC3.8은 대상 동작이 이미 대시보드에 있어 spec만 추가하면 됐지만, **AC3.7은 슬라이스 7의
화면 절반을 함께 당겨 왔다** — `/api/compare`는 이미 Gold 파생이었고 막힌 것은 `/compare`가
플레이스홀더라는 점 하나뿐이었기 때문이다. 상류 슬라이스(4~6)를 앞지른 것처럼 보이지만 배치
파이프라인 의존은 새로 생기지 않으며, 실집계 Gold가 붙으면 같은 화면이 그대로 실데이터를 받는다.

**화면 순서 근거**: 대시보드 척추(슬라이스 4) 이후 각 화면이 추가로 요구하는 파이프라인 능력의
한계 비용(작은 것 우선: `trend`)과 가치 우선순위, 운영 의존성(`reprocess`는 상류 전체가 실
구현이어야 하므로 최후)을 종합. 화면↔AC↔여정↔가치 매핑은
`docs/mockups/econ-opinion-monitor-mockup-index.md`를 SSOT로 따른다.
