## 1. 서비스 개요 (참고)

**경제 여론 추세 모니터** — 한국·미국·전세계 3축의 조회수 상위 경제 뉴스를 매시간 수집해, 서술 대상별 관심 추세와 분위기를 시각화한다.

## 2. 여정 정의

**대상 사용자 (페르소나)**
이도현(가명), 31세, 파이프라인 운영 데이터 엔지니어 (가정). 분석 프롬프트·로직과 배치 운영을 함께 맡는다. 로직을 고치기 전에 "틀린 게 모델인지, 입력인지, 우리 파서인지"부터 가려야 한다고 생각한다.

> **범위 주의**: P2 여정의 범위 확정은 `JRN-ingestion-recovery`와 동일한 미결 사항이다.

**진입 맥락**
두 경로로 들어온다. ⑴ **레코드에서**: 소비자 흐름(급등 검증·분위기 확인)에서 분류가 이상한 기사를 제보받거나, 원문 계보를 보다가 납득되지 않는 판단을 발견한다. ⑵ **실행에서**: 한 배치 실행의 미분석·호출 실패가 평소보다 많다는 운영 알림이나 정기 점검에서 들어온다.

**트리거**
특정 기사의 분석 결과(대상 국가·서술 대상·분위기·신뢰도 상태)가 본문 내용과 맞지 않아 보이거나, 한 실행에서 같은 증상의 결과가 몰려 나왔다.

**사용자 목표**
그 판단이 어떤 입력과 모델 응답에서 나왔는지 되짚어 원인을 입력(수집)·로직(프롬프트)·모델 응답·파싱·일회성 중 하나로 가르고, 알맞은 조치 흐름으로 넘긴다.

**완료 기준**
대상 레코드의 LLM 호출 기록(또는 미호출 사유)과 소속 실행 기록을 연 뒤 원인 분류를 하나 선택한 상태 — 조치가 필요한 분류면 인계 대상 여정으로 이동까지. 로그로는 호출 기록 열람 → 실행 기록 열람 → 원인 분류 선택 이벤트의 순서로 확인.

## 3. 단계별 상세

> 단계 식별자는 순번이 아닌 슬러그를 쓴다. 순서가 바뀌어도 식별자는 유지한다.

### `STP-pin-record` 의심 판단 특정

- **사용자 행동**: 이상해 보이는 분석 결과를 레코드 하나로 특정한다 — 제보 링크, 원문 계보, 또는 실행 기록의 증상 목록에서 (AC4.3, AC2.6)
- **터치포인트**: `JRN-judgment-debug.html` 결과 검색·선택(`CMP-table`), 운영 알림 카드 / 제보 채널(제품 외부)
- **생각·감정**: "이 기사가 왜 '긍정'이야? 금리 인상 기사인데"
- **페인포인트 / 이탈 위험**: 제보가 기사 제목만 들고 오면 같은 기사의 여러 관측·버전 중 무엇인지 헤맨다 → 소비자 화면의 기사 행마다 레코드 식별자를 품은 딥링크를 두어 이 여정으로 바로 진입

### `STP-read-exchange` LLM 요청·응답 열람

- **사용자 행동**: 호출 기록에서 전송 프롬프트, 가공 전 응답 원문, 파싱 결과를 나란히 읽는다. 재시도 횟수와 모델·파라미터·로직 버전도 확인한다 (AC4.2)
- **터치포인트**: `JRN-judgment-debug.html` 호출 기록(`CMP-kv`), 응답↔저장값 대조(`CMP-table`)
- **생각·감정**: "모델은 '혼합'이라고 답했는데 저장은 '긍정'이네… 파서가 문제다"
- **페인포인트 / 이탈 위험**: 파싱 결과만 보이고 응답 원문이 없으면 모델이 틀렸는지 파서가 틀렸는지 가를 수 없다 → 응답 원문과 파싱 결과를 필드 단위로 대조해 불일치를 강조

### `STP-check-input` 입력 점검

- **사용자 행동**: 모델이 실제로 받은 제목·본문이 Bronze 원문과 같은지, 본문이 비었거나 잘렸거나 다른 수정 버전인지 확인한다 (AC4.2, AC2.6, AC1.7)
- **터치포인트**: `JRN-judgment-debug.html` 입력 대조 — 전송 프롬프트 ↔ Bronze 본문 버전 이력
- **생각·감정**: "모델 잘못이 아니었네, 본문이 광고 문구뿐이었어"
- **페인포인트 / 이탈 위험**: 기사 본문이 여러 번 수정됐으면 어느 버전으로 판단했는지 헷갈린다 → 호출 기록이 가리킨 본문 버전을 버전 이력 위에 표시하고, 최신 버전과 다르면 배지로 알림

### `STP-scan-run` 같은 실행 훑기

- **사용자 행동**: 레코드가 속한 실행을 열어 단계별 건수·실패 사유·모델·로직 버전을 보고, 같은 증상(파싱 실패·호출 실패·저신뢰 등)이 그 실행에 얼마나 몰렸는지 확인한다 (AC4.1, AC4.3)
- **터치포인트**: `JRN-judgment-debug.html` 실행 단계 표(`PAT-integrity-panel` 계열), 증상 몰림 지표(`CMP-metric`)
- **생각·감정**: "이 기사만 그런 건지, 그 시간 실행 전체가 그런 건지부터 보자"
- **페인포인트 / 이탈 위험**: 스케줄러 이력은 최근 몇 건만 남아 지난주 실행은 이미 사라졌다 → 레이크의 실행 기록(AC4.1)을 원천으로 하고, 증상별 건수에서 해당 레코드 목록으로 바로 내려가게

### `STP-route-cause` 원인 판정과 인계

- **사용자 행동**: 원인을 입력(수집)·로직(프롬프트)·모델 응답·파싱·일회성 중 하나로 고르고, 조치가 필요하면 해당 여정으로 넘긴다
- **터치포인트**: `JRN-judgment-debug.html` 원인 판정 폼·인계 목록
- **생각·감정**: "프롬프트가 혼합 기준을 흐리게 적고 있어. 고쳐서 소급 적용하자"
- **페인포인트 / 이탈 위험**: 판정이 남지 않으면 같은 증상을 다음에 또 처음부터 조사한다 → 레코드·실행에 판정 메모를 남기고 같은 증상 조사 시 노출 (현재 AC 없음 — 백로그 후보)

## 4. 분기·예외 흐름

| 상황 | 처리 | 이어지는 단계 |
|---|---|---|
| 운영 알림으로 실행 단위에서 진입 | 실행 기록부터 열어 증상 유형을 고른 뒤 대표 레코드로 좁힌다 | `STP-scan-run` |
| 모델을 호출하지 않은 레코드 (본문 미확보 등) | 호출 기록 대신 미호출 사유를 보이고 입력 점검으로 바로 이동 | `STP-check-input` |
| 기존 응답을 재사용한 레코드 | 재사용 사실을 표시하고 원 호출 기록을 연다 | `STP-read-exchange` |
| 호출 기록이 없는 레코드 (기록 도입 이전) | 원문·실행 기록만으로 진행하고, 재현이 필요하면 표본 재분석으로 넘긴다 | `JRN-logic-backfill` · `STP-dry-run` |
| 입력(수집) 이상으로 판정 | 수집 복구 흐름으로 인계 | `JRN-ingestion-recovery` · `STP-locate-gap` |
| 로직·프롬프트 결함으로 판정 | 로직 수정 후 소급 적용 흐름으로 인계 | `JRN-logic-backfill` · `STP-scope-range` |
| 조사 도중 이탈 | 레코드 식별자 딥링크로 같은 레코드에 재진입 (판정 전 상태는 세션에만 유지 — 가정) | `STP-pin-record` |

외부 지연: 해당 없음 — 이 여정은 남은 기록을 읽기만 하고 모델을 다시 호출하지 않는다. 재현 호출이 필요하면 `JRN-logic-backfill`의 표본 재분석으로 넘기며, 그쪽이 모델 공급자 지연을 다룬다.
