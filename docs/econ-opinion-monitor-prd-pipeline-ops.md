# PRD: 파이프라인 실행 관측 (Batch Run Observability)

> 대응 요구사항: 파생 — "배치 처리 과정과 기사별 LLM 판단 과정을 사후에 열람·감사할 수 있어야 한다" (2026-09-24 신설)
> 데이터 레이크 계층: **계층 공통** (수집·분석·집계를 가로지르는 실행 기록)

## 달성 가치
- **V5 (원문 추적성·재처리)** — 결과가 어떤 실행에서, 어떤 입력과 모델 응답으로 만들어졌는지를 되짚을 수
  있게 해 결과의 설명·감사와 재처리 판단의 근거를 남긴다.

## 개요

AC2.6이 **분석 결과 → 원문** 방향의 역추적을 보장한다면, 이 PRD는 **분석 결과 → 그것을 만든 실행과
LLM 호출** 방향의 역추적, 그리고 실행 과정 자체의 열람을 보장한다.

배치는 매시간 수집 → 분석 → 집계를 한 번의 실행(run)으로 돈다. 지금 그 과정은 스케줄러 이력(성공·실패
각 최근 몇 건)과 단계별 표준 출력 로그에만 남는다. 시간이 지나면 사라지고, 어느 레코드가 어느 실행에서
만들어졌는지와도 연결되지 않는다. 기사별 LLM 응답은 분석 단계의 응답 재사용 캐시에 남지만, 성공한
응답만 저장되고 실행과의 연결이 없어 "이 판단이 왜 나왔나"를 되짚는 기록으로 쓸 수 없다.

### 설계 전제 — 기록 규모 (2026-09-24 운영 실측)

같은 제목·본문의 기사는 기존 응답을 재사용하므로, 새 LLM 응답은 매 주기 관측 건수가 아니라 새로
등장했거나 수정된 기사 수만큼 생긴다. 운영 실측으로 평시 시간당 0~43건, 하루 약 150~230건이고 응답은
평균 약 210자다. 로직 버전 전환 시에도 재호출은 최신 주기의 관측 건수(약 500건) 규모다. 따라서 이 PRD는
**보존 기간이나 용량 제한을 완료 조건으로 두지 않는다.** 규모가 달라지면 이 전제를 다시 판단한다.

### 범위 밖
- 이 기록을 보여 주는 **화면**(재처리 콘솔의 실행 타임라인, 원문 계보 화면의 호출 열람 등)은 사용자
  여정·목업 쪽 문서에서 정의한다. 이 PRD는 화면이 기댈 기록과 연결을 정의한다.
- LLM 판단의 **정확도** 평가는 범위 밖이다(분석 PRD와 골든 평가 하네스의 몫). 이 PRD는 판단이
  어떻게 만들어졌는지를 남길 뿐, 옳은지를 판정하지 않는다.

## Acceptance Criteria

### AC4.1: 배치 실행·단계 기록
- **설명**: 배치 실행마다 실행 ID, 트리거(정기/재처리), 시작·종료 시각, 최종 상태를 기록한다. 각
  단계(수집·분석·집계)마다 상태, 소요 시간, 입력 건수와 처리 결과별 건수, 실패 사유를 함께 기록한다.
  처리 결과는 단계에 맞게 나누되(예: 분석은 성공·저신뢰·미분석·호출 실패·응답 재사용·건너뜀), 결과별
  건수의 합이 입력 건수와 같아야 한다. 수집의 소스별 실패와 그 사유도 기록한다.
  기록은 데이터 레이크에 남아 스케줄러 이력 보존 한도나 파드 로그 보존과 무관하게 조회할 수 있어야
  한다. 중간에 실패·중단된 실행도 그 시점까지의 단계 기록을 남긴다.
- **달성 가치**: V5
- **검증 방법**: 정상 실행에서 단계 간 건수가 맞물리는지(앞 단계 출력 = 다음 단계 입력, 입력 = 결과별
  건수 합), 일부 소스 실패·분석 단계 중단 실행에서 실패 단계와 사유가 기록되는지, 스케줄러 이력이
  정리된 뒤에도 기록이 조회되는지 확인한다.

### AC4.2: 기사별 LLM 호출 기록
- **설명**: 분석 단계에서 기사마다 LLM에 보낸 요청과 받은 응답을 기록한다. 호출 기록은 실행 ID, 대상
  Bronze 레코드, 분석 로직 버전, 모델과 요청 파라미터, 전송 프롬프트(시스템·사용자), 가공 전 응답 원문,
  파싱 결과 또는 실패 사유, 재시도 횟수, 호출 시각과 소요 시간을 가진다.
  **파싱에 실패했거나 형식이 깨진 응답, 모델 호출 자체가 실패한 경우도 기록한다.** 기존 응답을
  재사용해 모델을 호출하지 않았다면, 그 사실과 재사용한 원 호출 기록을 남긴다.
  전송 프롬프트는 원문 그대로 저장하거나, 이미 보존된 구성 요소(프롬프트 템플릿, Bronze 제목·본문)에서
  바이트 단위로 같게 재구성할 수 있는 형태로 저장한다. 재구성 방식이면 전송본의 해시를 함께 저장해
  재구성본과의 일치를 검증할 수 있어야 한다.
  호출 기록은 append-only다. 재처리는 새 호출 기록을 추가하며 이전 기록을 덮어쓰거나 지우지 않는다.
- **달성 가치**: V5
- **검증 방법**: 정상 응답·파싱 실패 응답·호출 실패 각각에서 호출 기록이 남는지, 저장(또는 재구성)된
  프롬프트가 실제 전송본과 바이트 단위로 같은지, 응답 재사용 시 원 호출 기록으로 연결되는지, 재처리 후에도
  이전 호출 기록이 남는지 확인한다.

### AC4.3: 레코드 ↔ 실행 ↔ 호출 연결
- **설명**: 모든 Silver 분석 레코드는 자신을 만든 실행 ID와 호출 기록(응답을 재사용했다면 원 호출
  기록)을 가리킨다. 모델을 호출하지 않은 레코드(본문 미확보 등)는 호출하지 않은 사유를 가진다.
  반대로 실행 기록에서 그 실행이 만들거나 갱신한 레코드 목록과 호출 기록 목록으로 이동할 수 있어야 한다.
  AC2.6의 Bronze 추적 키와 함께, 임의 Silver 레코드에서 원문·호출·실행 세 방향으로 도달할 수 있다.
- **달성 가치**: V5
- **검증 방법**: 분석 완료·저신뢰·미분석 레코드 각각에서 호출 기록(또는 미호출 사유)과 실행 기록으로,
  실행 기록에서 해당 레코드 목록으로 양방향 도달되는지, 재처리로 병존하는 두 로직 버전의 레코드가 각자
  다른 실행·호출을 가리키는지 확인한다.
